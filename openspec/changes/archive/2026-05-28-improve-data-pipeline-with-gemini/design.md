## Context

The scraper currently contains both the legacy audio transcription spot-extraction path and the newer Gemini direct video extraction path. Gemini direct extraction is now the preferred source for spot mentions and presenter attribution, but some downstream pieces still reflect the older shape: exported data includes a separate `presenters` array, Gemini spot records do not store extracted addresses, and geocoding only has the spot name/context available.

This change makes Gemini direct extraction the source of truth, enriches its output with nullable spot addresses, uses those addresses during geocoding, and simplifies the frontend data contract by deriving presenters from exported spots.

## Goals / Non-Goals

**Goals:**

- Extend Gemini direct spot extraction to return and persist an optional address per spot.
- Improve the Gemini prompt so presenter names use canonical spelling from article/video titles when appropriate.
- Include stored addresses in geocoding requests when available.
- Include primary type display names in exported spot records.
- Remove the exported top-level `presenters` array and derive presenter filter values from spots in the frontend.
- Remove legacy transcription-based extraction code and clean up obsolete database data/schema.
- Reset existing Gemini-derived data and reprocess from scratch with the new prompt and geocoding behavior.

**Non-Goals:**

- Adding primary-type filtering to the frontend.
- Preserving backwards compatibility for the legacy transcription extraction flow.
- Keeping historical Gemini extraction data generated by the old prompt.

## Decisions

### Use Gemini direct extraction as the only spot extraction source

Remove legacy transcription and transcript-based spot extraction code instead of keeping it behind compatibility flags. The pipeline should route spot extraction through the Gemini direct flow only.

Alternatives considered:

- Keep both flows and hide the old flow from the CLI. This reduces short-term deletion risk, but continues carrying obsolete schema, tests, and maintenance burden.
- Keep transcription only for debugging/comparison. This is no longer needed if Gemini is trusted as the production flow.

### Store address on Gemini spot records as nullable text

Add an `address` field to Gemini spot extraction DTOs, response parsing, file artifacts, and the database table that stores Gemini spots. The field should be nullable/optional throughout because many videos will not expose a reliable address.

Alternatives considered:

- Store addresses only in exported JSON. This would make geocoding unable to use the address as a persisted intermediate result.
- Store addresses in a separate normalized table. That is unnecessary while each extracted spot mention has at most one Gemini-detected address.

### Treat Gemini addresses as hints, not authoritative corrections

The prompt should ask Gemini to return an address only when reasonably confident, especially when a transition card subtitle appears to contain an address. Geocoding should use the address when present, but the address should not replace the canonical spot name.

Alternatives considered:

- Require an address for every spot. This would increase hallucination risk.
- Ignore address unless manually verified. This would miss the intended geocoding quality improvement.

### Build Google Places Text Search requests from name plus optional address

Geocoding remains a normal Google Places API call, not an LLM call. The implementation should continue to use `POST https://places.googleapis.com/v1/places:searchText` with the existing Amsterdam `locationRestriction`, `languageCode`, API key header, and field mask. The only behavioral change is how the `textQuery` string is built.

When Gemini extracted an address, build `textQuery` from the spot name plus the address:

```text
<spot name>, <extracted address>
```

Example HTTP request:

```http
POST https://places.googleapis.com/v1/places:searchText
Content-Type: application/json
X-Goog-Api-Key: <PRODUCTION_GOOGLE_MAPS_API_KEY>
X-Goog-FieldMask: places.location,places.id,places.displayName.text,places.primaryType,places.primaryTypeDisplayName
Referer: https://fccentrummap.hkstm.dev/
```

```json
{
  "textQuery": "Café Binnenvisser, Bilderdijkstraat 36, Amsterdam",
  "languageCode": "nl",
  "locationRestriction": {
    "rectangle": {
      "low": {
        "latitude": 52.274525,
        "longitude": 4.711585
      },
      "high": {
        "latitude": 52.461764,
        "longitude": 5.073559
      }
    }
  }
}
```

When Gemini did not extract an address, keep the existing fallback query shape:

```json
{
  "textQuery": "Café Binnenvisser, Amsterdam",
  "languageCode": "nl",
  "locationRestriction": {
    "rectangle": {
      "low": {
        "latitude": 52.274525,
        "longitude": 4.711585
      },
      "high": {
        "latitude": 52.461764,
        "longitude": 5.073559
      }
    }
  }
}
```

The address is only a disambiguating input hint for Google Places lookup. It should not replace the persisted spot name, exported spot name, or correction display name.

Alternatives considered:

- Geocode by address only. This may lose useful venue-name context and can be ambiguous for shared addresses.
- Add a separate Google API field for address. The current Places Text Search endpoint accepts the lookup string through `textQuery`, so the address should be incorporated into that string rather than sent as a separate JSON field.
- Keep current name-only geocoding. This does not use the new extraction signal.

### Derive presenters from spots on the frontend

Remove the exported top-level `presenters` collection. The frontend should compute unique presenter names from the `spots` array and use that derived list for filtering UI state.

Alternatives considered:

- Keep the `presenters` array as a denormalized convenience. This preserves the existing contract but duplicates information and makes exports harder to reason about.

### Reset generated Gemini and geocoding data

Because the prompt and geocoding inputs change, existing Gemini spot data should be dropped and regenerated. Any dependent geocoding output should also be regenerated so coordinates reflect address-aware queries.

Alternatives considered:

- Migrate old Gemini rows by adding `NULL` addresses. This would keep stale extraction output and miss the improved prompt behavior.

## Gemini Prompt Template

The Gemini direct prompt should be updated to make address extraction and canonical presenter spelling explicit. The exact implementation may still be constructed in Go, but the resulting prompt should be equivalent to:

```text
You are an assistant extracting "De spots van" location recommendations from public URL context.

Use the article_url and youtube_url below as the primary source inputs.

Goal:
- Find the primary presenter.
- Find the Amsterdam spots that are actually recommended in the article/video.
- Return only places supported by evidence or notes.
- Do not invent places, addresses, or timestamps.

Presenter guidance:
- Use the article title and video title to determine the canonical presenter name.
- Prefer the spelling used in the title when it appears to represent the name the person is known by.
- If the presenter is unknown, omit presenter_name.

Address guidance:
- For each spot, include address only if reasonably confident.
- Many videos show a transition card between spots with the spot name.
- Often the subtitle on that card contains the address, but not always.
- Do not guess. If unsure, omit address or return null.

Timestamps:
- Timestamps are YouTube timestamps in seconds from the start of the video.
- If a timestamp is unknown, omit it instead of guessing.

Confidence:
- For each spot, include a numeric confidence value between 0.0 and 1.0 when possible.
- Use higher values only when the spot is clearly supported by the article/video.
- If confidence cannot be estimated, omit confidence instead of guessing.

[source_inputs]
article_url: <article_url>
youtube_url: <youtube_url>

Return only JSON matching exactly this response shape:

{
  "article_url": "<article_url>",
  "youtube_url": "<youtube_url>",
  "presenter_name": "<optional primary presenter name or null>",
  "spots": [
    {
      "place": "<place name>",
      "address": "<optional detected address or null>",
      "youtubeTimestampSeconds": 123,
      "evidence": "<source fragment or short rationale>",
      "confidence": "<number from 0.0 to 1.0 indicating Gemini's confidence, or omit if unknown>"
    }
  ]
}
```

## Database Schema After This Change

The final schema should remove the legacy transcription-path tables and keep only the article, presenter, Gemini direct, geocode, and correction tables needed by the new flow.

### `article_sources`

```sql
CREATE TABLE IF NOT EXISTS article_sources (
  article_source_id INTEGER PRIMARY KEY AUTOINCREMENT,
  url TEXT NOT NULL UNIQUE,
  published_at TIMESTAMP,
  discovered_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### `article_fetches`

```sql
CREATE TABLE IF NOT EXISTS article_fetches (
  article_fetch_id INTEGER PRIMARY KEY AUTOINCREMENT,
  article_source_id INTEGER NOT NULL UNIQUE
    REFERENCES article_sources(article_source_id) ON DELETE CASCADE,
  html TEXT NOT NULL,
  fetched_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### `presenters`

```sql
CREATE TABLE IF NOT EXISTS presenters (
  presenter_id INTEGER PRIMARY KEY AUTOINCREMENT,
  presenter_name TEXT NOT NULL UNIQUE,
  materialized_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### `article_presenters`

```sql
CREATE TABLE IF NOT EXISTS article_presenters (
  article_source_id INTEGER NOT NULL
    REFERENCES article_sources(article_source_id) ON DELETE CASCADE,
  presenter_id INTEGER NOT NULL
    REFERENCES presenters(presenter_id) ON DELETE CASCADE,
  linked_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (article_source_id, presenter_id)
);
```

### `gemini_direct_spot_mentions`

```sql
CREATE TABLE IF NOT EXISTS gemini_direct_spot_mentions (
  gemini_direct_spot_mention_id INTEGER PRIMARY KEY AUTOINCREMENT,
  article_source_id INTEGER NOT NULL
    REFERENCES article_sources(article_source_id) ON DELETE CASCADE,
  youtube_url TEXT NOT NULL,
  place TEXT NOT NULL,
  address TEXT,
  youtube_timestamp_seconds REAL CHECK (youtube_timestamp_seconds IS NULL OR youtube_timestamp_seconds >= 0),
  evidence TEXT,
  confidence REAL CHECK (confidence IS NULL OR (confidence >= 0 AND confidence <= 1)),
  model TEXT,
  extracted_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE(article_source_id, place)
);
```

### `gemini_direct_spot_google_geocodes`

```sql
CREATE TABLE IF NOT EXISTS gemini_direct_spot_google_geocodes (
  gemini_direct_spot_google_geocode_id INTEGER PRIMARY KEY AUTOINCREMENT,
  gemini_direct_spot_mention_id INTEGER NOT NULL UNIQUE
    REFERENCES gemini_direct_spot_mentions(gemini_direct_spot_mention_id) ON DELETE CASCADE,
  google_place_id TEXT,
  latitude REAL NOT NULL,
  longitude REAL NOT NULL,
  formatted_address TEXT,
  primary_type TEXT,
  primary_type_display_name TEXT,
  status TEXT NOT NULL,
  geocoded_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

### `gemini_direct_article_spots`

```sql
CREATE TABLE IF NOT EXISTS gemini_direct_article_spots (
  article_source_id INTEGER NOT NULL
    REFERENCES article_sources(article_source_id) ON DELETE CASCADE,
  gemini_direct_spot_google_geocode_id INTEGER NOT NULL
    REFERENCES gemini_direct_spot_google_geocodes(gemini_direct_spot_google_geocode_id) ON DELETE CASCADE,
  linked_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (article_source_id, gemini_direct_spot_google_geocode_id)
);
```

### `gemini_direct_spot_corrections`

```sql
CREATE TABLE IF NOT EXISTS gemini_direct_spot_corrections (
  spot_id TEXT PRIMARY KEY CHECK (trim(spot_id) <> ''),
  spot_name TEXT,
  place_id TEXT,
  latitude REAL,
  longitude REAL,
  youtube_timestamp_seconds INTEGER CHECK (youtube_timestamp_seconds IS NULL OR youtube_timestamp_seconds >= 0),
  hidden INTEGER NOT NULL DEFAULT 0 CHECK (hidden IN (0, 1)),
  created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CHECK (
    ((place_id IS NULL OR trim(place_id) = '') AND latitude IS NULL AND longitude IS NULL)
    OR (place_id IS NOT NULL AND trim(place_id) <> '' AND latitude IS NOT NULL AND longitude IS NOT NULL)
  )
);
```

Removed legacy or now-unused extraction tables:

- `article_texts`
- `audio_sources`
- `audio_transcriptions`
- `spot_mentions`
- `spot_google_geocodes`
- `article_spots`
- `spot_corrections`

`article_texts.cleaned_text` was only used as prompt context for the old transcript-based extraction path. The Gemini direct path sends Gemini the article URL and YouTube URL, so the cleaned article-text artifact is no longer needed after this change. `article_fetches` remains because fetched HTML is still useful for article metadata such as published date and for extracting/falling back to the YouTube URL.

## Risks / Trade-offs

- Gemini may hallucinate or over-infer addresses → Mitigate with prompt wording that requires reasonable confidence and with nullable storage.
- Removing legacy transcription code may delete useful debugging paths → Mitigate by relying on version control history and keeping the Gemini flow well tested.
- Export contract changes may break frontend assumptions → Mitigate by updating frontend types/tests to derive presenters from spots.
- Dropping existing Gemini/geocoding data requires a full rerun → Mitigate by documenting the reset and making the pipeline rerun path explicit.
- Address-aware geocoding may change existing coordinates → Mitigate by reviewing geocoding results after the full rerun.

## Open Questions

None at this time. The proposal makes the key direction explicit: Gemini direct extraction becomes the only spot extraction flow, previous Gemini data is discarded, and the pipeline is rerun from scratch.
